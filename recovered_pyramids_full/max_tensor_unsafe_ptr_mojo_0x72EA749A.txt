#[derive(Debug, Hash, Eq, PartialEq, Clone, Copy)]
pub enum Capability {
ClipboardIsolation,
NetworkIsolation,
GpuPassthrough,
UsbIsolation,
WaylandSecurityContexts,
}
pub struct RuntimeDescriptor {
pub name: &'static str,
pub capabilities: HashSet<Capability>,
}
pub struct SchedulingConstraint {
pub required: HashSet<Capability>,
pub preferred: HashSet<Capability>,
}
pub fn schedule_runtime(
constraints: &SchedulingConstraint,
available_backends: &[RuntimeDescriptor],
) -> Result<&'static str, &'static str> {
// Filter backends that satisfy 100% of required capabilities
let viable_backends: Vec<&RuntimeDescriptor> = available_backends
.iter()
.filter(|backend| constraints.required.is_subset(&backend.capabilities))
.collect();
if viable_backends.is_empty() {
return Err("SchedulingFailed: No local runtime backend satisfies the required capability graph.");
}
// Rank viable backends by how many 'preferred' capabilities they satisfy
let chosen = viable_backends
.into_iter()
.max_by_key(|backend| {
backend.capabilities.intersection(&constraints.preferred).count()
})
.unwrap();
Ok(chosen.name)
}

Answering the Device Mediation Hard Questions
To deliver on this v5 architecture, the control plane enforces four clean rules to solve your hard design choices:
Can two sessions share one GPU? Yes. Modern AMD and Intel GPUs support native DRI render node sharing, while enterprise NVIDIA assets use vGPU splitting. The device broker dynamically maps the target container's /dev/dri/renderD128 node but wraps it inside a strict cgroup v2 memory limitation path, preventing memory exhaustion attacks on the shared host VRAM.
Can a banking session see a USB smart card? Only if explicitly declared in the signed manifest. The device broker unbinds the hardware device node from the host kernel driver path and reconstructs it specifically inside the user's targeted sandbox using custom udev / sysfs filtering rules.
Can a gaming session access a microphone? No, unless the manifest contains the AudioCapture capability. By default, ohrd passes an empty virtual pipewire loopback device into unprivileged container spaces.
Can a browser paste data from another workload? Only through an explicit IPC clipboard broker manag
ed by the supervisor. The raw Wayland socket clipboard functionality is completely cut off by our capability engine. If data transfer is necessary, it must occur via an explicit, authenticated D-Bus request mediated by the control plane
The architectural foundation you have laid out for ohrd v5 correctly identifies the paradigm shift: treating the desktop environment as an untrusted, multi-tenant workload where the host kernel and control plane act strictly as a hardware multiplexer and security barrier.
However, looking critically at the provided implementation, there are several structural mismatches, naive assumptions about Linux device boundaries, and incomplete execution models that would cause this architecture to fail under production security audits or complex real-world hardware constraints.
1. Architectural Auditing & Critique
The Scheduler Illusion
In your main.rs example, your scheduler correctly selects the cage backend because it satisfies 100% of the required capabilities (ClipboardIsolation, NetworkIsolation). It then drops gamescope because it lacks those required capabilities.
However, immediately afterward, the control plane provisions a DeviceAllocationPlan with allow_gpu: true. The cage backend descriptor explicitly lacks the GpuPassthrough capability in its definition. The control plane is granting hardware access to a runtime that has not declared the capability to manage or isolate it safely.
Correction: The scheduling phase must output not just a backend string, but a validated Execution Context that marries the runtime's actual capabilities with the allowed device allocation plan. If a backend cannot explicitly claim a capability, the device broker must not provision it, even if requested by the manifest.
The Cgroups v2 / Device Node Fallacy
